## Analysis of the 7 failed requests (appended after the run, from Loki)
The 7 failures are HTTP 000: the traffic generator's 2-second client timeout,
not error responses. Traefik's access logs for 13:38:50-13:39:25 UTC (from Loki;
the node's own log files had already rotated after the load test) show
62 x 200 and 6 x 499 (client closed), and no 5xx. The slow responses (1-5s) came
from four different API pods, and one request spent only 0.21s inside Traefik,
so the delay was mostly before the ingress. That is a CPU spike across the
laptop's Docker VM while two crash-looping bad-release pods and a replacement
pod were starting, not a fault in the release path. The old version never
stopped serving and the rollback completed. Earlier runs of this demo had 0
failures; on a real cluster, CPU requests sized for startup and a retry
policy for idempotent GETs at the ingress would absorb it.
